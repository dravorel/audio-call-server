# Audio Call Server

Серверное приложение на Python для обмена аудиоданными между участниками 
одной комнаты в режиме реального времени.

Сервер принимает аудиофрагменты от клиентов по HTTP, сохраняет их в памяти 
и возвращает аудиоданные других участников той же комнаты в ответ на запрос.

Поддерживается обмен аудиоданными небольшими фрагментами (chunks), фильтрация 
уже полученных фрагментов по временным меткам, разделение участников по комнатам 
и автоматическое удаление устаревших аудиоданных.

## 📋 Требования

- Python 3.10+.
- Flask.

## 🛠️ Установка

1. Клонируйте репозиторий
    ```bash
    git clone <URL>
    cd <project-directory>
    ```

2. Создайте виртуальное окружения
    ```bash
    python -m venv .venv
    ```

3. Активируйте виртуальное окружение
    ```bash
    source .venv/bin/activate  # Linux / MacOS
    .venv\Scripts\activate     # Windows
    ```

4. Установите зависимости
    ```bash
    pip install -r requirements.txt
    ```

## ▶️ Запуск

Запустите основной файл приложения:

```bash
python src/main.py
```

По умолчанию Flask запускает сервер на локальном адресе `127.0.0.1:5000`.

## 🧩 Принцип работы

Сервер использует модель обмена аудиоданными, при которой каждый клиент 
одновременно отправляет собственные аудиофрагменты и получает аудиофрагменты 
других участников комнаты.

### 1. Приём аудио

Клиент отправляет HTTP POST-запрос с типом содержимого `multipart/form-data`.

Запрос содержит два поля:

- `audio` — бинарные данные аудио в формате Opus.
- `metadata` — JSON с метаданными аудиофрагмента и временем последнего запроса клиента.

### 2. Разделение по комнатам

Для хранения аудиоданных используется словарь `ROOMS`, в котором каждой комнате 
соответствует отдельная очередь аудиофрагментов. 
В качестве ключа используется идентификатор комнаты (`room_id`).

### 3. Хранение аудиофрагментов

Полученный аудиофрагмент добавляется в очередь соответствующей комнаты. Д
ля хранения используются объекты `AudioChunk`, содержащие:

- Индекс аудиофрагмента (`index`).
- Идентификатор отправителя (`user_id`).
- Временную метку создания (`timestamp`).
- Продолжительность аудио (`duration`).
- Используемый кодек (`codec`).
- Частоту дискретизации (`sample_rate`).
- Количество каналов (`channels`).
- Бинарные аудиоданные (`data`).

Все аудиоданные хранятся непосредственно в оперативной памяти сервера.

### 4. Удаление устаревших данных

Перед обработкой очередного запроса сервер проверяет очереди всех комнат и 
удаляет устаревшие аудиофрагменты. Время хранения определяется параметром 
`AUDIO_CHUNK_LIFETIME`. 

### 5. Выбор аудиоданных для отправки

После сохранения нового аудиофрагмента сервер формирует ответ клиенту. 
В ответ включаются только те аудиофрагменты из текущей комнаты, которые 
удовлетворяют двум условиям:

- Временная метка фрагмента больше `requested_timestamp`, переданного клиентом.
- Идентификатор отправителя (`user_id`) отличается от идентификатора отправителя текущего запроса.

### 6. Формирование ответа

Каждый аудиофрагмент преобразуется в последовательность байтов, состоящую из:

1. JSON с метаданными аудиофрагмента.
2. Разделителя `CHUNK_DATA_SEPARATOR`.
3. Бинарных аудиоданных.

Если для передачи подготовлено несколько аудиофрагментов, они объединяются с 
помощью разделителя `CHUNK_SEPARATOR`. Сервер возвращает результат в HTTP-ответе 
с MIME-типом `application/octet-stream`. Если подходящих аудиофрагментов нет, 
сервер возвращает пустой ответ.

## 🌐 Сетевой протокол

### Получение текущего времени

```http
GET /api/time
```

Endpoint возвращает текущее время сервера в формате Unix timestamp 
(количество секунд с 1 января 1970 года).

Формат ответа:

```http
Content-Type: application/json
```

```json
{
  "timestamp": 1234567890.0
}
```

Где:

- `timestamp` — текущее Unix-время сервера в секундах (тип `float`).

### Синхронизация аудиоданных

Для обмена аудиоданными используется HTTP POST с типом содержимого `multipart/form-data`.

#### Endpoint

```http
POST /api/<room_id>/sync
```

Где:

- `room_id` — идентификатор комнаты, в которой происходит обмен аудиоданными.

#### Формат запроса

Запрос содержит два multipart-поля:
- `metadata` — json метаданные запроса.
- `audio` — бинарные данные аудиофрагмента.

Поле `metadata`:

```json
{
  "format_version": 1,
  "requested_timestamp": 1234567890.0,
  "chunk": {
    "index": 1,
    "user_id": "1a2b3c4d5e6f",
    "timestamp": 1234567890.0,
    "duration": 0.5,
    "codec": "opus",
    "sample_rate": 48000,
    "channels": 1
  }
}
```

#### Формат ответа

Сервер возвращает бинарные данные с MIME-типом:

```http
Content-Type: application/octet-stream
```

Структура ответа:

```text
<metadata><CHUNK_DATA_SEPARATOR><audio_data>
<CHUNK_SEPARATOR>
<metadata><CHUNK_DATA_SEPARATOR><audio_data>
<CHUNK_SEPARATOR>
<metadata><CHUNK_DATA_SEPARATOR><audio_data>
...
```

Где:

- `metadata` — JSON с метаданными аудиофрагмента.
- `CHUNK_DATA_SEPARATOR` — разделитель между метаданными и бинарными аудиоданными.
- `audio_data` — бинарные данные аудиофрагмента.
- `CHUNK_SEPARATOR` — разделитель между соседними аудиофрагментами.

При отсутствии новых аудиоданных возвращается пустой ответ.

## 🗂️ Хранение данных

Сервер использует оперативную память для временного хранения аудиофрагментов.

Особенности хранения:

- Каждая комната имеет собственную очередь аудиофрагментов.
- Аудиоданные не сохраняются на диск.
- После перезапуска сервера все очереди очищаются.
- Устаревшие аудиофрагменты удаляются автоматически при обработке запросов.
- Данные разных комнат не смешиваются.
